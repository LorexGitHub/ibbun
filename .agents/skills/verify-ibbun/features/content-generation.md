# content-generation

Admin slice with no screens yet. It is the `content.generate`, `batch-text.generate` and `practice.generate` job handlers in `apps/worker`; the journeys below drive it through the queue and read the result from Postgres.

## Sub-features

- **Example Sentences** for a Word, a levelled Kanji or a Grammar Point (`kinds/example-sentence/`): Draft Sentence, Example and accepted answer with `generated` Provenance.
- **Japanese Explanations** for a Word sense ja Wiktionary doesn't cover, or a Grammar Point (`kinds/explanation/`): a Draft `japanese_explanation` with `generated` Provenance. A matching ja Wiktionary entry goes into the prompt as reference and into the Provenance `inputs`.
- **Batch Texts** (`kinds/reading-passage/`): `batch-text.generate` opens a Generation Request (`kind = batch-text`, target = a passage id derived from Learner and batch, `reason` carries the batch) and enqueues `content.generate`. The attempt writes a Draft Reading Passage (prose, Sentences linked in order) and the Learner's Batch Text record in `progress.texts`. The prompt carries the earlier items (weakest first), a target length that grows with the level's progress, the rotated passage type, and the cast and episode summary of the last episode at that level.
- **Merge proposals** (`kinds/proposals/merge.ts`, kind `merge_proposal`): target is a hanabira Grammar Point (`source_key.dataset = 'hanabira'`); candidates are the Grammar Points keyed `tanos`. Writes a `merge proposal` queue entry, no record.
- **Sense-alignment proposals** (`kinds/proposals/alignment.ts`, kind `sense_alignment`): target is an approved Word; its draft Japanese Explanations keyed `wiktionary-ja` are aligned to its JMdict senses. Writes one `sense alignment` queue entry per gloss.
- **Batch Texts** (`kinds/reading-passage/`): `batch-text.generate` opens a Generation Request (`kind = batch-text`, target = a passage id derived from Learner and batch, `reason` carries the batch) and enqueues `content.generate`. The attempt writes a Draft Reading Passage (prose, Sentences linked in order) and the Learner's Batch Text record in `progress.texts`. The prompt carries the earlier items (weakest first), a target length that grows with the level's progress, the rotated passage type, and the cast and episode summary of the last episode at that level.
- **Merge proposals** (`kinds/proposals/merge.ts`, kind `merge_proposal`): target is a hanabira Grammar Point (`source_key.dataset = 'hanabira'`); candidates are the Grammar Points keyed `tanos`. Writes a `merge proposal` queue entry, no record.
- **Sense-alignment proposals** (`kinds/proposals/alignment.ts`, kind `sense_alignment`): target is an approved Word; its draft Japanese Explanations keyed `wiktionary-ja` are aligned to its JMdict senses. Writes one `sense alignment` queue entry per gloss.
- **Practice Texts** (`kinds/practice-text/`, request `kind = 'practice-text'`): `practice.generate` `{ learnerId, practiceTextId }` looks up the Practice Text record `reading` or `listening` already wrote in `progress.texts` (its choices: level, form, passage type, length, topic) and opens a request whose target is the record's `passageId`. The attempt writes a Draft Reading Passage: `form = prose` for a passage, or `form = dialogue` with `passage_contains_sentence.speaker` (男/女) on every line and 2 `comprehension_questions`. Dialogue lines and task types per level come from `kinds/dialogue/config.ts`; `listening.synthesise` voices each line by that stored speaker. The prompt gives the Learner's weakest Known items of the level (weakest first, about one per 50 characters or one per dialogue line) and asks for at least half. No record for the id, or a request already open for the passage: nothing happens.
- **Grammar Point fields and Matcher Rule** (`kinds/grammar-fields/`, request `kind = 'grammar-fields'`): updates the draft point's `grammar_point` row in place (title, forms, formation, register, meaning, `matcher_rule`; `notes` is left alone) and adds `generated` Provenance. The point stays `draft`. A rule that misses any of the point's own tokenised example Sentences is refused as an invalid answer, so the attempt is spent and the model sees why.
- **Single-Sentence clip selection** (`kinds/clip-selection/`, `clipSelection(auth, config).select(studyItemId)`): no LLM, no Generation Request or Run. For a levelled Word or Grammar Point it picks, from the item's approved, non-retired Examples, the Sentence with 0 unlevelled Words that is closest to the level's length band (characters; `DEFAULT_BANDS`), ties broken by the lowest `sha256(studyItemId:sentenceId)`. It writes an approved `listening_clip` Study Item (`kind = sentence`, derived Provenance `clip-selection/1` with inputs `[studyItemId, sentenceId]`) and one `clip_voices_sentence` row with a voice from the allow-list at `hash(sentenceId) mod size`, `audio_key` null. Nothing qualifies: no clip. Run again after Examples change: a clip whose Sentence no longer qualifies is retired (an Approval Decision `retired`, decider `derived`) and the rule picks again. Not yet called by a job or by the app.
- **Listening dialogues** (`kinds/dialogue/`, request `kind = 'dialogue'`, target = an approved, levelled Grammar Point): writes a Draft `listening_clip` Study Item whose id is the request id, a `listening_clip` row with `kind = 'dialogue'`, one Draft `sentence` per line linked by `clip_voices_sentence` (position, `speaker` 男/女, one VOICEVOX voice per speaker), and 2 Draft `example` rows on the clip, each with a `comprehension_question` (correct option first, `answer = 0`). All share one `generated` Provenance. Lines per level are 4/6/8/10/12 from N5 to N1. The two 聴解 task types rotate per dialogue (概要理解 from N3). `requestDialogues(auth, jobs)` opens and starts one request per levelled Grammar Point that never had one.
- **Audio synthesis** (`kinds/synthesise/`, job `listening.synthesise`; no LLM, no Generation Request): speaks an approved Sentence, or every line of an approved dialogue Reading Passage, with VOICEVOX. The kana is built from the Sentence's tokens, the file is Ogg Opus at speed 1 in the audio store (`AUDIO_DIR`, one file per key) and the key is a hash of kana, voice, engine version and speed. The voice comes from `VOICE_ALLOW_LIST` by hash(Sentence ID) mod length; a dialogue gets one male-sounding and one female-sounding voice by hash(passage ID). Sets `sentence.audio_key` and `audio_voice`, fills any non-retired `clip_voices_sentence` line for the Sentence, and approves with a derived decision `listening.synthesise` / engine version. When `VOICEVOX_URL` is a Lambda function URL (`*.lambda-url.<region>.on.aws`), `platform/tts` signs every call with SigV4 from the role's `AWS_*` credentials (#253); any other URL is called unsigned. The Lambda image is `docker/voicevox` (VOICEVOX plus the AWS Lambda Web Adapter); Compose still runs the stock image.
- **Generation Runs**: one per LLM call (model, template version, inputs, tokens, cost), including calls that gave no usable answer.
- **Attempts**: 3 per Generation Request, then `generation failed` in the queue.
- **Daily token budget**: the Learner-triggered pool (Batch Texts and Practice Texts) at most 50%, the rest for everything else; a spent pool pauses its work and queues `budget exhausted` naming the pool (`learner` or `general`).

## How to get to it (user POV)

There is no Learner or admin screen. The supervisor sees its effects in the Content Approval queue (`generation failed`, `budget exhausted`) once `content-approval` exists. Until then, check the tables.

## Driving it with Playwright

Nothing to drive in a browser yet. Journey (API and database only):

1. Start the stack (`verify-ibbun` launch). Set `ANTHROPIC_API_KEY`, or stub the LLM; `DAILY_TOKEN_BUDGET` defaults to 2,000,000.
2. Open a request: insert a `content_graph.generation_request` row with `kind = 'examples'`, `status = 'open'`, `attempts = 0` for an approved Word, then enqueue `content.generate` with `{ "requestId": "<id>" }`.
3. Expect: a `generation_run` row for the request with tokens and cost; draft `sentence`, `example` and `example_answer` rows whose `provenance.source.kind = 'generated'` and `generationRunId` is that run; the request `in review`; a `content.review` job queued.
4. Budget: set `DAILY_TOKEN_BUDGET=100`, repeat. The second request stays `open` with 0 attempts and one unresolved `queue_entry` with reason `budget exhausted` and `detail.pool = 'general'`.

5. Batch Text: enqueue `batch-text.generate` with `{ learnerId, level: "N5", itemIds: [<approved Word id>] }`. Expect: a `batch-text` request `in review` with one Generation Run; a draft `reading_passage` (id = the request's `target_id`) with draft `sentence` rows linked by `passage_contains_sentence`; one `progress.texts` row (`kind = batch`, `episode = 1`, `detail` holding the cast and summary); a `content.review` job. Enqueue it again: nothing changes. Enqueue a second batch: `episode = 2`, and the prompt (Generation Run `inputs`) has the first episode's summary.
6. Proposals: open a `merge_proposal` request for a draft hanabira Grammar Point (with at least one `tanos` Grammar Point), or a `sense_alignment` request for a Word with draft `wiktionary-ja` explanations. Expect unresolved `queue_entry` rows with reason `merge proposal` / `sense alignment`, `generation_run_id` set, `detail` holding the proposed match and a reason, and the request `in review`. `content.review` fails until the proposals rubric (#88) exists.

7. Explanations: insert a request with `kind = 'explanation'` for an approved `word_sense` id (or a Grammar Point study item id) and enqueue `content.generate`. Expect a draft `japanese_explanation` row (`word_sense_id` or `grammar_point_id` set) with `generated` Provenance. A sense that already has a non-rejected explanation uses its 3 attempts and lands in the queue as `generation failed`. For a Grammar Point with a `wiktionary-ja` explanation, the draft's Provenance `inputs` contain that explanation's id and the Generation Run `inputs` contain its text.
5. Grammar fields: for a `draft` Grammar Point with an empty `meaning`, insert a request with `kind = 'grammar-fields'` and enqueue `content.generate`. Expect the `grammar_point` row filled, `matcher_rule` a `{ "pattern": [...] }` object, the study item still `draft`, the request `in review`. With example Sentences that have tokens, the stored rule matches each of them.
6. Dialogues: insert a request with `kind = 'dialogue'` for an approved Grammar Point with a `level_candidate`, and enqueue `content.generate`. Expect a draft `study_item` (`type = 'listening_clip'`, id = the request id), a `listening_clip` row with `kind = 'dialogue'`, draft `sentence` rows linked in order by `clip_voices_sentence` with alternating 男/女 speakers and two different voices, and 2 draft `example` rows on the clip whose `comprehension_question` has 4 choices. Every one of these rows has the same `provenance_id`. An unlevelled Grammar Point uses its 3 attempts and lands in the queue as `generation failed`.

8. Audio: set `VOICEVOX_URL`, `AUDIO_DIR` and `VOICE_ALLOW_LIST` (JSON, 4–6 `{id, character, speaker}` with both `男` and `女`), then enqueue `listening.synthesise` with `{ "target": { "kind": "sentence", "sentenceId": "<approved Sentence with tokens>" } }`. Expect `sentence.audio_key` set, a file of that name in `AUDIO_DIR` (Ogg Opus), `audio_voice` = the hashed allow-list voice, and one derived `approval_decision` (`decider.process = 'listening.synthesise'`). Enqueue it again: nothing changes. For `{ "kind": "dialogue", "passageId": ... }` on an approved `form = 'dialogue'` passage: its Sentences alternate between two different voices, 男 first.

8. Practice Text: insert a `progress.texts` row (`kind = practice`, level N5, form `passage` or `dialogue`, a fresh `passage_id`, passage type, length), then enqueue `practice.generate` with `{ learnerId, practiceTextId: <its id>, level: "N5", kind }`. Expect a `practice-text` request `in review` with `target_id` = that `passage_id`, a draft `reading_passage` of the right `form` (dialogue: `speaker` on every line, 2 questions) and a `content.review` job. Give the Learner Known N5 items first and the Generation Run `inputs` list them, weakest first. Enqueue it again: nothing changes.

Preconditions: Postgres from Compose with migrations applied; an approved Word with a form and a level.

## Gotchas

- Audio synthesis refuses a draft or retired Sentence, a Sentence with no tokens, and a passage that is not an approved dialogue, so the job fails and is retried. Tokens carry no pitch, so every accent phrase is accented on its last mora (flat); a dictionary pitch accent is not used yet.

- A retry of a Batch Text rewrites the same passage id: the rejected attempt's links are retired. The Batch Text record is written once, with the first attempt, so its cast and summary come from that attempt.
- Earlier items, and a Practice Text's weakest Known items, are ordered by Mastery, then soonest due; `progress` does not expose stability.
- `practice.generate` does not write the Practice Text record: the enqueuing slice records it first (that is what counts toward the 5-per-24 h limit) and passes its id.
- Practice Texts have no reviewer rubric yet (#91); `content.review` throws for them until it exists.
- A paused request is not retried by the queue. `resumePaused()` re-enqueues open requests whose pool has budget again; nothing calls it on a schedule yet.
- Grammar fields have no reviewer rubric yet (`content-approval` has none for `grammar-fields`); `content.review` will throw for these requests until that slice adds one.
- Drafts have no tokens until `content-approval` runs Sudachi, and the generator's whole-Sentence reading is not stored, so reading check 2 compares only the target's reading (kept as the accepted answer).
- A retry of a dialogue rewrites the same clip: the rejected attempt's `clip_voices_sentence` links and Examples are retired, and new ones are written.
- Nothing calls `requestDialogues` on a schedule yet, and `content-approval` has no dialogue rubric until #92, so `content.review` throws for dialogue requests.
- The budget counts Generation Runs, so reviewer calls count only once `content-approval` records them as runs.
- Clip selection has no entry point outside code yet, so check it with its unit tests (`pnpm vitest run slices/content-generation/kinds/clip-selection`) or call `select()` against a seeded database. The clip has no `computed_level` row until the levels rebuild runs, and no audio until `listening.synthesise` exists.

8. VOICEVOX Lambda image (#253): `docker build -t mojibun-voicevox-lambda docker/voicevox`, download `aws-lambda-rie` (x86_64), then `node scripts/measure-voicevox-lambda.mjs <path to aws-lambda-rie>`. Expect one row per memory size (2, 3 and 4 GB) with a cold start under 10 s and clips of a few seconds; at 3 GB about 3 s for a 3 s sentence. Signed calls: `pnpm vitest run platform/tts` (signatures pinned to the AWS SDK's signer).
