# import

The supervisor sees every Import Run at `/admin/import`: dataset, upstream version, status, what the run added, changed and retired, which overrides it left Stale or Orphaned, which Examples it sent back to Draft, which Study Items it Suspended, and a link into the Content Approval queue filtered to the run. Runs start themselves from `worker` schedules: JMdict and KANJIDIC2 (with KRADFILE) on the first Monday of each month (retried daily until it lands) from jmdict-simplified, yomitan-jlpt-vocab (Word JLPT Levels) checked every Monday and applied only on a new release, Tatoeba on Saturday and Sunday noon UTC after the Saturday 06:30 export, and a daily staleness check that queues a `staleness alarm` when live JMdict or KANJIDIC2 data is older than 31 days. Nobody starts them.

## Sub-features

- **Import Run** (`slices/import/server/run.ts`): stage (fetch and parse), diff against the latest snapshot, apply through `content-graph/authoring.applySnapshot()`, report. A rerun of an applied or breaker-held version changes nothing and downloads nothing.
- **Snapshot and raw files**: the latest normalised snapshot per dataset in Postgres (`import.snapshot`, `import.snapshot_record`); the raw files of the last 3 runs per dataset under `IMPORT_RAW_DIR` (default `./data/import-raw`). `IMPORT_RAW_DIR=s3://bucket/prefix` keeps them in S3 instead (`<dataset>/<version>/<name>` plus `<dataset>/runs.json`, the kept versions oldest first); locally, `docker compose up -d s3` and set `AWS_ENDPOINT_URL_S3=http://localhost:8333` with any `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`. A held run is released by replaying from those files.
- **Scheduled jobs**: `import.jmdict` and `import.kanjidic` (each daily 12:00 UTC, runs only when the monthly refresh is due), `import.kanjivg` (Mondays 12:00 UTC; downloads and applies only when the latest GitHub release tag of KanjiVG/kanjivg is new), `import.yomitan` (Mondays 08:00 UTC; a rerun of the live release changes nothing), `import.tatoeba` (Sat and Sun 12:00 UTC; an already applied export is a no-op), `import.wiktionary-ja` (Mondays 12:00 UTC; a no-op until kaikki.org shows a new extraction date), `import.unidic` (Mondays 12:00 UTC; a no-op until the NINJAL download page links a new `unidic-cwj-<yyyymm>` stamp) and `import.tanos` (daily 13:00 UTC; one archived snapshot, so it lands once and later firings do nothing) and `import.staleness` (daily 07:00 UTC), started by `apps/worker`.
- **Where each refresh runs on AWS** (`slices/import/server/tasks.ts`, #258): each `refreshes()` entry has a `home`. `lambda` runs in the worker Lambda (15-minute limit). `fargate` (JMdict, Tatoeba: 17 and 20 minutes for a first import on a laptop) makes the job call `ECS.RunTask` and return; the task runs `slices/import/server/import-task.ts` from the worker image with `IMPORT_DATASET` and `IMPORT_RELEASE`, then exits. The launcher exists only when `IMPORT_TASK_CLUSTER`, `IMPORT_TASK_DEFINITION` and `IMPORT_TASK_SUBNETS` are set (optional `IMPORT_TASK_SECURITY_GROUPS`, `IMPORT_TASK_CONTAINER`, default `import`); without them, as locally, every refresh runs in the worker. A task already running for the dataset (`startedBy: import.<dataset>`) means no second one, so a twice-delivered job imports once. Proof: `npx vitest run slices/import/server/tasks.test.ts slices/import/server/jobs.test.ts`. Run one refresh as the task does: `DATABASE_URL=postgres://ibbun:ibbun@host.docker.internal:5432/ibbun bash slices/import/smoke/import-task.sh kanjivg` (2 vCPU, 4 GB; `CPUS=1 MEMORY=1769m` for Lambda's share). Expect `import.kanjivg: done in <n> s` and an `applied` row in `content_graph.import_run`. `pnpm content:import` prints each step's duration.
- **Report screen** (`GET /api/import/runs`, supervisor only; screen at `/admin/import`).
- **Sources** live in `slices/import/sources/<source>/`. Built: Tanos kanji lists (`sources/tanos-kanji`: the five archived `jlpt<n>/kanji/` pages of Wayback snapshot `20200117222855`, parsed once into one List Level Candidate per Kanji, easiest level wins a collision; the KANJIDIC2 `jlpt` cross-check is not part of this seed), Tatoeba (`sources/tatoeba`: per-language `jpn`/`eng` exports, `jpn_indices.csv`, bzip2 via `seek-bzip`; tokens from the Sudachi sidecar `SUDACHI_URL`, so it must be running), yomitan-jlpt-vocab (`sources/yomitan-jlpt-vocab/`: downloads `original_data/n5.csv`…`n1.csv` at the release tag, because the release zip has no `ent_seq`; keeps the easiest level of a Word on two lists; skips rows with no or several matches; reports each in the worker log), JMdict, KANJIDIC2 + KRADFILE (`kanjidic2-all` and `kradfile` files of the same jmdict-simplified release; every character, English meanings only, `strokes` empty until the KanjiVG seed). KanjiVG (`sources/kanjivg`, from its own GitHub releases). ja Wiktionary (`sources/ja-wiktionary`: the kaikki.org wiktextract dump of the Japanese edition, one record per Japanese gloss keyed `title#entry.gloss`; version is the extraction date; redirect stubs, cross-reference glosses and other languages are skipped). UniDic (`sources/unidic-pitch`: the `unidic-cwj-<stamp>_full.zip` holds `lex.csv`, which the plain zip lacks, so `download` reads only `lex.csv` (29 MB deflated, kept as `lex.csv.deflate`) and `license/BSD` out of the 3 GB zip by HTTP range requests; one record per dictionary-form lexeme with an `aType`, about 352,000 on 202512, keyed `form\treading` with the reading in hiragana). The rest are separate Seed issues. Grammar seed: see below.
- **KanjiVG strokes** (rule `kanjivg` in core): one record per character keyed by code point (`098df`), its SVG stroke paths in order, written to `content_graph.kanji.strokes` of the KANJIDIC2 Kanji with that literal. Code points KANJIDIC2 lacks are skipped; a character that leaves KanjiVG loses its strokes, not its Kanji.
- **Grammar Point seed** (`slices/import/sources/grammar-seed/`, one-time, no schedule): job `import.grammar-seed`, started by hand, needs `DATABASE_URL`, `SUDACHI_URL` and `ANTHROPIC_API_KEY` for the merge proposals. It downloads hanabira's five `grammar_json` level files at the latest commit of tristcoil/hanabira.org-japanese-content and the five Tanos level list pages (Wayback Machine snapshot, since tanos.co.uk no longer resolves), then seeds 828 hanabira and about 287 Tanos Grammar Points as `draft` with a `list` Level Candidate, hanabira's example Sentences as `draft` with `draft` demonstrates links, and one `merge_proposal` Generation Request per hanabira point. A second run does nothing (it finds the `hanabira` Import Run).
- **Matcher Rule runs** (`slices/import/sources/matcher-runs/`): job `import.matcher-runs`, started by hand or after Grammar Points are approved; needs `DATABASE_URL`. It runs every approved Grammar Point's Matcher Rule over every approved, non-retired Sentence and inserts `draft` `sentence_demonstrates_grammar` links with a `derived` Provenance (`matcher-run`). A link keyed by (Sentence, Grammar Point, span) is never inserted twice, in any state, so approved and rejected decisions survive. Each approved Grammar Point under 5 approved, non-retired Examples gets an `examples` Generation Request and a `content.generate` job, unless one is already open.
- **Everything at once** (`pnpm content:import`, `slices/import/server/import-all.ts`, entry `import-cli.ts`): runs every source in schedule-list order (JMdict, KANJIDIC2, KanjiVG, Tatoeba, yomitan, ja Wiktionary, UniDic, Tanos), then the grammar seed, the derived-link rebuild, the level rebuild and the Matcher Rule runs, and prints one line per step. Needs `DATABASE_URL` and Sudachi up; no worker. It refuses a database that holds the N5 fixture, before any download. The first failing step stops the command; a rerun skips every dataset already applied at its upstream version.
- **Derived-link rebuild** (`slices/import/sources/derived-links`, `rebuildDerivedLinks({ authoring })`): recomputes Word contains Kanji, Sudachi Sentence uses Word (only for Sentences no other process linked), single-Sentence Listening Clip voices Sentence and superseded by from the live graph, and writes only the difference. Links are replaced through core `removeDerivedLinks`, never retired. A change of `DERIVED_PROCESS_VERSION` replaces every link. Started by `pnpm content:import` only; no job or schedule runs it. Proof: `npx vitest run slices/import/sources/derived-links`; run it twice against a seeded database and expect `{ added: 0, removed: 0 }` the second time: `psql "$DATABASE_URL" -c "select count(*) from content_graph.word_contains_kanji"` is unchanged.
- **Publish to the showcase stage** (`pnpm content:publish`, `slices/import/server/publish.ts`, entry `publish-cli.ts`, ADR 0017): migrates `TARGET_DATABASE_URL`, upserts approved, non-retired Content Graph records from `DATABASE_URL` in dependency order (a record is copied only if everything it points at was), then uploads the audio files they name from `AUDIO_DIR` to `TARGET_AUDIO_DIR` (`s3://bucket/audio/`), skipping keys already there. A second run changes nothing. Nothing is deleted from the target. Tested over two PGlite databases and an in-memory audio target; the CLI itself needs a real S3.
- **Apply rules** (core, built): `applySnapshot` for `jmdict`, `kanjidic`, `kanjivg`, `tatoeba`, `tanos`, `yomitan`, `wiktionary-ja` and `unidic`. `tanos` records are Approved `list` Level Candidates on the KANJIDIC2 Kanji with that literal (Provenance CC BY, author Jonathan Waller, source URL the archive snapshot); a literal KANJIDIC2 lacks is skipped and named in the run's report notes, and with no KANJIDIC2 Kanji at all the run fails instead of applying nothing. A ja Wiktionary gloss becomes a Draft Japanese Explanation (CC BY-SA 4.0, Provenance link to `https://ja.wiktionary.org/wiki/<title>`) on the first sense of the one JLPT Word (it has a Level Candidate) whose kanji form, or kana reading if it has no kanji form, equals the page title. A page that fits no Word or several Words is skipped and offered again next run. The first gloss for a Word opens a `sense_alignment` Generation Request; the proposals it makes go to the Content Approval queue as `sense alignment`. `yomitan` records are List Level Candidates (Approved, CC BY-SA 4.0, credited to Waller via stephenmk) on the JMdict Word with that `ent_seq`; an `ent_seq` JMdict lacks is skipped and named in the report `notes`; a run that changes the current level of more than 100 Words trips the breaker. Its proof is `npx vitest run core/content-graph/src/authoring/snapshot`.  A ja Wiktionary gloss becomes a Draft Japanese Explanation (CC BY-SA 4.0, Provenance link to `https://ja.wiktionary.org/wiki/<title>`) on the first sense of the one JLPT Word (it has a Level Candidate) whose kanji form, or kana reading if it has no kanji form, equals the page title. A page that fits no Word or several Words is skipped and offered again next run. ## How to get to it (user POV)

1. Log in as the supervisor.
2. Open **Import** in the nav, or go to `/admin/import`.
3. Read the newest run. Held runs (circuit breaker) are listed first. Follow **Open in the Content Approval queue** to the run's flagged items.

## Driving it with Playwright

Preconditions: baseline from the README, plus `verify.sh` must also start `pnpm --filter @ibbun/worker start` (it does not yet) and the API needs `AUTH_SECRET` and `APP_URL` set so the report API mounts. A supervisor must exist (`pnpm --filter @ibbun/learner grant-supervisor`, after sign-up in the account slice). JMdict is about 11 MB from GitHub, so the first run needs internet and takes a few minutes.

- **Report is supervisor-only**: `curl -s -o /dev/null -w '%{http_code}' $WEB/api/import/runs` with no cookie. Expect `401`. With a plain Learner's cookie, expect `403`.
- **Empty state**: as the supervisor, open `/admin/import` before any run. Expect the heading "Import Runs" and "No Import Run yet".
- **Run starts by itself**: with the worker running, wait for the next `import.jmdict` firing, or enqueue it once: `psql "$DATABASE_URL" -c "select * from jobs.job where name='import.jmdict'"`. Expect one run to reach status `applied`; `/admin/import` shows "jmdict <release tag>" with a non-zero **added** and a link to `/admin/content-approval?importRun=<id>`.
- **KANJIDIC2 run**: enqueue `import.kanjidic` the same way. Expect one `applied` run for dataset `kanjidic` with about 13,100 added; `psql "$DATABASE_URL" -c "select literal, meanings, on_readings, kun_readings, grade, frequency, components from content_graph.kanji where literal = '食'"` shows eat/food, ショク, grade 2, frequency 328. 12,156 Kanji have components (KRADFILE has none for the rest).
- **ja Wiktionary run**: needs JMdict and the JLPT level seed (yomitan) applied first. Enqueue `import.wiktionary-ja`. Expect one `applied` run, about 166,000 records parsed (15 s). `psql "$DATABASE_URL" -c "select e.text, p.licence, p.source_url from content_graph.japanese_explanation e join content_graph.provenance p on p.id = e.provenance_id where e.approval='draft' limit 5"` shows `cc-by-sa-4.0` and a `ja.wiktionary.org/wiki/` link on every row, and `select count(*) from content_graph.generation_request where kind='sense_alignment'` is non-zero once any Word matched.
- **Tanos kanji run**: after the KANJIDIC2 run, enqueue `import.tanos` the same way (first run needs internet: five pages from web.archive.org). Expect one `applied` run for dataset `tanos`, upstream version `20200117222855`, with at most 2,211 added (N5 79, N4 166, N3 367, N2 367, N1 1,232; no Kanji is on two lists; any not in KANJIDIC2 are skipped and named in the report). Stored value: `psql "$DATABASE_URL" -c "select k.literal, c.level, c.kind, c.approval, p.licence, p.author from content_graph.level_candidate c join content_graph.kanji k on k.study_item_id = c.study_item_id join content_graph.provenance p on p.id = c.provenance_id where k.literal in ('日','食','会')"`. Expect `日` N5, `食` N5, `会` N4, kind `list`, approval `approved`, licence `cc-by`, author `Jonathan Waller`. `/credits` then shows the Tanos line with version `20200117222855`.
- **Tanos before KANJIDIC2 fails safe**: on an empty database, enqueue `import.tanos` first. Expect the job to fail with "import KANJIDIC2 first" and no `tanos` row in `content_graph.import_run`.
- **UniDic run**: needs JMdict applied first (accents attach to its readings). Enqueue `import.unidic`. The first run downloads about 30 MB by range request and parses in about 4 s. Expect an `applied` run for dataset `unidic`; `psql "$DATABASE_URL" -c "select r.text, r.pitch_accent, p.licence, p.author from content_graph.word_reading r join content_graph.provenance p on p.id = r.provenance_id where r.text in ('たべる','はし') and r.pitch_accent is not null"` shows `{2}` for たべる with `bsd-3-clause` and the NINJAL author. Compounds UniDic splits into several tokens keep `null`. A JMdict refresh keeps the accent. Proof without the network: `npx vitest run slices/import/sources/unidic-pitch core/content-graph/src/authoring/snapshot`.
- **Idempotent rerun**: fire the job again. Expect no new row in `content_graph.import_run` and no new download in the worker log.
- **Word levels land**: after `import.jmdict` has applied, enqueue `import.yomitan`. Expect an `import_run` row for dataset `yomitan` with `counts.added` about 7.7k, and `psql "$DATABASE_URL" -c "select level, count(*) from content_graph.level_candidate where kind='list' group by 1"` showing rows for N5 to N1. Run it before JMdict and every row is skipped, with the first run's `added` at 0.
- **Staleness alarm**: `psql "$DATABASE_URL" -c "update content_graph.import_run set applied_at = now() - interval '40 days' where dataset='jmdict'"`, fire `import.staleness`. Expect one unresolved `content_graph.queue_entry` with reason `staleness alarm` and `detail.dataset = 'jmdict'`.
- **Second view of the stored value** for every journey: `psql "$DATABASE_URL" -c "select dataset, upstream_version, status, counts from content_graph.import_run order by applied_at desc nulls first"`.

- **KanjiVG applies only on a new tag**: fire `import.kanjivg` twice (`psql "$DATABASE_URL" -c "select * from jobs.job where name='import.kanjivg'"`). Expect one `content_graph.import_run` row with dataset `kanjivg` and upstream version `r<date>`, and no second download. Needs KANJIDIC2 applied first or every record is skipped (`added` = 0). Second view: `psql "$DATABASE_URL" -c "select literal, cardinality(strokes) from content_graph.kanji where literal='食'"`. Expect 9.

## Tatoeba

- **Proof without the network**: `npx vitest run slices/import/sources/tatoeba core/content-graph/src/authoring/snapshot slices/import/server/run.test.ts`.
- **Live run**: needs `SUDACHI_URL` up, JMdict applied first (links resolve against Words), and about 100 MB of downloads. Fire `import.tatoeba`. Expect an `applied` run; `select approval, count(*) from content_graph.sentence group by 1` shows only `draft`; `select count(*) from content_graph.sentence_uses_word` is non-zero; a sentence's provenance row carries the Tatoeba username and `https://tatoeba.org/sentences/show/<id>`.
- **Translation rule**: for a Sentence with several English translations the lowest id owned by a native English speaker (skill level 5 in `eng_user_languages`) is stored, else the lowest id.
- **Links**: `jpn_indices` links win for a Sentence it covers; Sudachi lemma links only for the rest. Not run end to end against the live export by the author (unit tests use fixtures).
- **Grammar seed**: enqueue `import.grammar-seed` once (`aws sqs send-message --endpoint-url http://localhost:9324 --queue-url "$JOBS_QUEUE_URL" --message-body '{"name":"import.grammar-seed","payload":{}}'` with any AWS credentials). Expect `select dataset, upstream_version, status from content_graph.import_run where dataset in ('hanabira','tanos-grammar')` to show two `applied` rows; `select count(*) from content_graph.grammar_point` about 1,115; `select count(*) from content_graph.sentence_demonstrates_grammar where approval='draft'` about 3,310; `select count(*) from content_graph.generation_request where kind='merge_proposal'` 828. Enqueue it again: no new rows.
- **Matcher Rule runs**: enqueue `import.matcher-runs` (`psql "$DATABASE_URL"` into `jobs.job`). Expect new rows in `select approval, count(*) from content_graph.sentence_demonstrates_grammar group by 1` as `draft` only, and `select count(*) from content_graph.generation_request where kind='examples' and reason='matcher run'` equal to the approved Grammar Points with a rule and under 5 approved Examples. Enqueue again: counts unchanged. Approve one link, rerun: it stays `approved` and no duplicate span appears.

## Gotchas

- ja Wiktionary: kanji spellings that are stubs pointing to a kana page (食べる, 会う) get no gloss yet; only entries on the headword page are imported (research: about two thirds of JLPT Words). Gaps go to the Japanese Explanation generator. Run on the real 2026-11-02 dump (parse only, no Compose stack).
- The `import` Postgres schema holds the slice's private tables. `import` is not a reserved word, but quote it in ad-hoc SQL if a client complains.
- A run held by the circuit breaker applies nothing and leaves only an `import_run` row (`breaker tripped`) and one `breaker tripped` queue entry. Releasing it is a rerun with `{ "release": true }`, which uses the kept raw files.
- Not run against the live release by the author; the parser was run on the real 3.6.2 files (13,108 characters).
- jmdict-simplified publishes only a `common` flag, so Word `priorityTags` is `["common"]` or `[]`. Pitch accent is `null` until `import.unidic` has applied.
- The Content Approval queue screen is another slice. Until it ships, the link from the report goes to a route the shell answers with its home fallback.
- `yomitan` rows join JMdict through `source_key`, so the dataset only does anything after JMdict is live. Collisions and CSV rows with no JMdict match go to the worker log, not the report screen. The unit tests (`npx vitest run slices/import/sources/yomitan-jlpt-vocab core/content-graph/src/authoring/snapshot`) cover them.
- Not run end to end against the Compose stack by the author: no supervisor login exists until the account slice ships. The unit and Postgres tests cover the run, the schedule logic, the API roles and the screen.
- KanjiVG is a ~3.6 MB `.xml.gz` release asset; the first run needs internet. Not run end to end against the Compose stack by the author. The parser was checked against the real r20260714 file (6703 characters).
- KANJIDIC2 never rewrites `strokes` (it creates Kanji with none); only the `kanjivg` rule does. A KANJIDIC2 refresh keeps KanjiVG strokes and does not count the Kanji as changed.
- Grammar seed: not run against live hanabira, Tanos or Sudachi by the author. The parsers were run on the real files (828 hanabira points with 3,310 examples; Tanos N5 40, N4 50, N3 63, N2 63, N1 71 entries). The seeded Grammar Points have hanabira's free-text formation split on `+`, not structured slots; generation of fields, the level rule on merge and the merge itself are later steps.
- Matcher Rule runs: proven by `npx vitest run slices/import/sources/matcher-runs` on the core fake; not run against live Postgres or the queue by the author, and `mutator` could not run on the author's Windows machine (symlink privilege), so CI is its first run.
